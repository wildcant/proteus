# Modules

A module owns one domain's data and the behaviour over it: cart, customer, product, payment, order,
pricing, inventory, fulfillment, notification, auth, file, user.

Every module is a private local container of repositories with **exactly one service exposed** to the
shared container. Nothing else crosses the boundary — no repository, no model, no helper. Another
module that needs this one's data asks its service, and orchestration that spans two modules is not a
module's job at all; it is a workflow. This is enforced by `no-module-internals` and
`no-cross-module-imports` in `deps-analyzer/.dependency-cruiser.cjs`.

`index.ts` is that boundary, declared once:

```ts
export default Module(Modules.INVENTORY, {
  service: InventoryModuleService,
  models,
  repositories: { inventoryItemRepository: InventoryItemRepository /* … */ },
})
```

A module too large for one service class splits *internally*: the service constructs the collaborator
from its own injected dependencies and keeps it private (`ProductOptionService` inside `product`).
Splitting into two modules is usually not the alternative — the cascade graph is built per module from
one `models/` barrel, so tables with foreign keys between them must share a module.

## File Structure

```
src/modules/<name>/
├── models/                  # Drizzle pgTable() + index.ts barrel
├── repositories/            # BaseRepository extensions + index.ts barrel
├── services/                # the module service, its private collaborators, index.ts barrel
├── migrations/              # generated by drizzle-kit (+ meta/)
├── __tests__/               # every test, including pure-function ones
├── utils/                   # optional — pure helpers a service consumes
├── loaders/                 # optional — provider registration into the local container
├── providers/               # optional — a provider that ships with the module
├── database.config.ts       # drizzle-kit config
├── provider-declarations.ts # optional — the configured providers
├── sync-providers.ts        # optional — out-of-band provider upsert for workerd
└── index.ts                 # Module() definition
```

Only `index.ts` and `services/` are universal. A module that owns no tables has no `models/`,
`repositories/`, `migrations/` or `database.config.ts` — `file` is the one today, being a thin
front for its providers.

## What May Live Here

Eight folders and four root files, and that list is closed:

| Path | Holds |
|------|-------|
| `models/` | Drizzle tables; the barrel is what the cascade graph is built from |
| `repositories/` | `BaseRepository(table)` extensions, constructed with `{ getDb }` |
| `services/` | The module service and any collaborator it keeps private |
| `migrations/` | drizzle-kit output — regenerated in place, never hand-edited |
| `__tests__/` | Every test the module has |
| `utils/` | Pure helpers a service consumes (`payment/utils/idempotency-keys.ts`) |
| `loaders/` | Provider registration into the module's local container |
| `providers/` | A provider that ships with the module (`payment/providers/system.ts`) |
| `index.ts` | The `Module()` definition — the module's whole public surface |
| `database.config.ts` | drizzle-kit config, read by `db:generate` and `db:migrate` |
| `provider-declarations.ts` | The configured providers, read by both DI and the seed |
| `sync-providers.ts` | Out-of-band provider upsert for workerd, where loaders cannot write |

A ninth folder or a fifth root file is invisible to bootstrap and to drizzle-kit — both read
`index.ts` and `database.config.ts` and nothing else — so it becomes a private convention only its own
module follows. Every kind of code already has a home: a table in `models/`, data access in
`repositories/`, business logic on the service, a pure helper in `utils/`.

Enforced by **`module-holds-only-known-file-kinds`** in `deps-analyzer/.dependency-cruiser.cjs`.
Nesting *inside* the eight folders is unconstrained, which `migrations/meta/`,
`__tests__/fixtures/` and `payment/loaders/__tests__/` all rely on.

## Where Tests Go

In `__tests__/`, never beside the file they cover — including pure-function tests, which is why
`option-combinations.test.ts` sits in `product/__tests__/` and not next to its source in
`product/utils/`. One place to look holds both kinds, and the folder is what tells a reader the
difference between a module file and a file *about* a module file. `__tests__/` may nest.

Enforced by **`module-tests-live-in-a-tests-folder`** in `deps-analyzer/.dependency-cruiser.cjs`.

## Where a Provider Goes

`providers/` inside a module is for the built-in that ships with it — `payment/providers/system.ts`,
`fulfillment/providers/manual.ts`. Both import only from `core/`: no SDK, no credentials, nothing to
configure.

**A provider that integrates a third party goes in `src/providers/`**, outside every module, so that
`no-module-internals` catches it the moment it reaches for a repository. See
[`src/providers/README.md`](../providers/README.md).
