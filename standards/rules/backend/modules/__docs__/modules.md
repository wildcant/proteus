# Modules

A module owns one domain's data and the behaviour over it: auth, cart, customer, file, fulfillment,
inventory, notification, order, payment, pricing, product, region, store, user. This covers what a
module is, the closed list of files it may hold, and what its tables must carry.

Building a new one from nothing is the ten steps in [adding a module](./adding-a-module.md).

## Structure

```
src/modules/<name>/
├── models/                  # Drizzle pgTable(), one table per file
├── repositories/            # BaseRepository extensions, imported by name
├── services/                # the module service and its private collaborators
├── migrations/              # generated by drizzle-kit (+ meta/)
├── __tests__/               # every test, including pure-function ones
├── utils/                   # optional — pure helpers a service consumes
├── loaders/                 # optional — provider registration into the local container
├── providers/               # optional — a provider that ships with the module
├── database.config.ts       # drizzle-kit config
├── provider-declarations.ts # optional — the configured providers
├── sync-providers.ts        # optional — out-of-band provider upsert for workerd
└── index.ts                 # Module() definition
```

Only `index.ts` and `services/` are universal. A module that owns no tables has no `models/`,
`repositories/`, `migrations/` or `database.config.ts` — `file` is the one today, being a thin front
for its providers.

## Shape

`index.ts` is the boundary, declared once:

```ts
export default Module(Modules.INVENTORY, {
  service: InventoryModuleService,
  models,
  repositories: { inventoryItemRepository: InventoryItemRepository /* … */ },
})
```

## Rules

### Exactly one service crosses the boundary

Every module is a private local container of repositories with **exactly one service exposed** to the
shared container. Nothing else crosses — no repository, no model, no helper. Another module that
needs this one's data asks its service, and orchestration that spans two modules is not a module's
job at all; it is a [workflow](../../workflows/__docs__/workflows.md).

A module too large for one service class splits *internally*: the service constructs the collaborator
from its own injected dependencies and keeps it private (`ProductOptionService` inside `product`).
Nothing registers or exports it, so the public surface stays one service. Splitting into two
*modules* is usually not the alternative — the cascade graph is built per module from the `models`
object of its definition, so tables with foreign keys between them must share a module.

### Eight folders and four root files, and that list is closed

| Path | Holds |
|------|-------|
| `models/` | Drizzle tables, one per file; `index.ts` names them all in `models` |
| `repositories/` | `BaseRepository(table)` extensions, constructed with `{ getDb }` |
| `services/` | The module service and any collaborator it keeps private |
| `migrations/` | drizzle-kit output — regenerated in place, never hand-edited |
| `__tests__/` | Every test the module has |
| `utils/` | Pure helpers a service consumes (`payment/utils/idempotency-keys.ts`) |
| `loaders/` | Provider registration into the module's local container |
| `providers/` | A provider that ships with the module (`payment/providers/system.ts`) |
| `index.ts` | The `Module()` definition — the module's whole public surface |
| `database.config.ts` | drizzle-kit config, read by `db:generate` and `db:migrate` |
| `provider-declarations.ts` | The configured providers, read by both DI and the seed |
| `sync-providers.ts` | Out-of-band provider upsert for workerd, where loaders cannot write |

A ninth folder or a fifth root file is invisible to bootstrap and to drizzle-kit — both read
`index.ts` and `database.config.ts` and nothing else — so it becomes a private convention only its
own module follows. Every kind of code already has a home: a table in `models/`, data access in
`repositories/`, business logic on the service, a pure helper in `utils/`. Widen the rule
deliberately rather than working around it.

Nesting *inside* the eight folders is unconstrained, which `migrations/meta/`, `__tests__/fixtures/`
and `payment/loaders/__tests__/` all rely on.

### There are no barrels

A module has no `index.ts` inside `models/`, `repositories/` or `services/`. Import the file:
`from './repositories/product-variant.js'`, never `from './repositories/index.js'`.

The concrete path states which of nine you took; a barrel hides it, and dependency-cruiser resolves
through it less precisely. A barrel over `services/` would also be the one place a cycle could
start — seven module services import a private collaborator from their own folder, and routing that
through a barrel makes `services/index.ts → product-module-service.ts → services/index.ts`.

`models/` had one until the two things that needed the namespace whole stopped needing it. Drizzle's
schema is now `src/schema.gen.ts`, generated by enumerating the model files, and the cascade graph is
built from the `models` object of the `Module()` definition — which is a better list than the barrel
was, because it is the one the code actually reads. `model-reaches-cascade-graph` checks every such
list is complete, and finds them by searching for the two shapes that build a graph rather than by
naming the files that do, so a new one is covered the day it is written. See ADR 0016.

The rule for any folder added later is the same one that emptied these: a barrel exists only where
something consumes the namespace *whole*, and when it does, say which consumer and why.

### Every table spreads `...timestamps`

A table's `createdAt`, `updatedAt` and `deletedAt` come from one helper in `core/db/columns.ts`,
spread into the column object:

```ts
export const inventoryItemTable = pgTable('inventory_item', {
  id: text().primaryKey().default(sql`CONCAT('iitem_', REPLACE(gen_random_uuid()::text, '-', ''))`),
  sku: text(),
  ...timestamps,
})
```

`deletedAt` is what makes a row soft-deletable, and `BaseRepository` filters on it automatically. A
table without it is **destroy-only**: the cascade walker hard-deletes it and nothing can restore it.
That is a decision to state in a suppression comment, not one to make by omitting three characters.
The walker, the guards it derives and what a deletion reaches are in
[`docs/soft-delete-cascade.md`](../../../../../docs/soft-delete-cascade.md).

### Tests live in `__tests__/`, never beside the file they cover

Including pure-function tests, which is why `option-combinations.test.ts` sits in
`product/__tests__/` and not next to its source in `product/utils/`. One place to look holds both
kinds, and the folder is what tells a reader the difference between a module file and a file *about*
a module file. `__tests__/` may nest.

### A third-party provider lives outside every module

`providers/` inside a module is for the built-in that ships with it — `payment/providers/system.ts`,
`fulfillment/providers/manual.ts`. Both import only from `core/`: no SDK, no credentials, nothing to
configure.

**A provider that integrates a third party goes in `src/providers/`**, outside every module, so that
`layer-graph-providers` catches it the moment it reaches for a repository — `providers` may import
`core` and nothing else under `src/`, so nothing in `src/providers/` can import a module at all. See
[`src/providers/README.md`](../../../../../apps/backend/src/providers/README.md).

## Enforcement

| Rule id | The paragraph it enforces |
|---|---|
| `model-without-standard-timestamps` | that every table spreads `...timestamps`, so it has a `deletedAt` |
| `layer-graph-*` | that only `container.ts`, `schema.gen.ts` and `link-modules/` may name a module at all — and so, from the other side, that a third-party provider outside every module cannot reach a repository |
| `no-cross-module-imports` | that a module never reaches into another module |
| `module-holds-only-known-file-kinds` | the eight folders and four root files, and nothing else |
| `module-tests-live-in-a-tests-folder` | that every test is under `__tests__/` |

The first is an ast-grep rule under `standards/rules/backend/modules/`; the other four are
dependency-cruiser rules in `apps/backend/structure/.dependency-cruiser.cjs`, run by the `structure`
gate. `standards/README.md` covers how each kind runs and how to suppress one.

### Exemptions

A table that genuinely must be destroy-only carries an `ast-grep-ignore` at the declaration
with the reason written above it — `--error=unused-suppression` then fails the day it outlives its
reason, which is what the previous central exemption map keyed by table name could not do.

## What is deliberately not enforced

- **What a service may be shaped like.** Read methods delegate straight to the repository and write
  methods wrap in `this.withTransaction`; helpers are `private` methods on the class rather than
  module-level functions. All three are conventions with no rule behind them —
  "is this method a write" is the same unanswerable question that makes
  [`route-chains-mutations-on-one-service`](../../api/__docs__/route-helpers.md) key on a verb
  prefix list. [Adding a module](./adding-a-module.md) has the shape to copy.
- **That `InjectedDependencies` matches the `Module()` definition.** The repository keys have to
  agree across two files; a mismatch is a resolution failure at boot rather than a shape ast-grep can
  see. Typecheck catches the half that is a type.
- **The cascade facts.** Whether a relationship cascades, which column an index leads with, whether a
  predicate excludes soft-deleted rows and what one deletion reaches are all properties of the object
  drizzle builds, not of the source that builds it. They are checked by
  `apps/backend/scripts/checks/` instead, and `standards/README.md` records the verdict per check.
- **Whether `docs/soft-delete-cascade.md` should fold in here.** It spans `src/modules/` *and*
  `apps/backend/scripts/checks/`, so it stays in `docs/` under the ownership test. Revisiting that is
  its own question, not this document's.

## Relationship with workflows

A module never calls another module. What needs two of them to change together is a
[workflow](../../workflows/__docs__/workflows.md), and what needs two of them only to be *read* stays
in the route handler — see [route helpers](../../api/__docs__/route-helpers.md).
